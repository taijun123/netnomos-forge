# 办公室趣味 Demo 与财务/网络 Demo 使用案例

> 当前状态：已完成主集成。本文用于演示脚本、产品讲述和验收沟通。办公室前端已迁入当前 `web` 应用并接入 `office_demo` 后端；财务和网络场景使用 `netnomos-forge` 当前 W4 稳定管线。

## 1. 统一演示故事

演示主线是“用显式规则控制模型输出”：

1. 用户把业务资料或网络流量资料交给系统。
2. 系统学习或加载规则，并把规则解释成业务可读语言。
3. 系统用规则检查新资料，找出违反勾稽、协议或物理约束的记录。
4. 用户要求模型生成报告或记录。
5. A 轨展示裸模型可能流畅但不可靠的输出。
6. B 轨展示规则约束、投影修正和终检后的输出。
7. 办公室趣味 UI 用多智能体角色把这些步骤变成可观察的流程。

## 2. 场景一：办公室趣味工作流总览

### 2.1 目标用户

- 需要快速理解系统工作流的非技术观众。
- 需要向管理层或客户展示“多智能体协作”的产品团队。
- 需要把规则、数据、报告和聊天能力串成统一体验的主集成负责人。

### 2.2 用户故事

用户打开 3D 办公室，看见 6 个角色各自负责流程一环：

- 主管 A 监管任务；
- 快递 B 接收数据；
- 员工 C 学习规则；
- 员工 D 验证规则；
- 员工 E 生成报告；
- 产品经理 F 进行受控聊天。

后端 SSE 事件会驱动右侧任务日志，办公室页面加载、规则接入、数据接入都会触发真实 `office_demo` workflow。

### 2.3 演示步骤建议

1. 展示办公室主屏，说明 6 个角色不是纯装饰，而是后端阶段的可视化映射。
2. 点击规则集面板，展示财务组、网络组、输出约束组。
3. 点击数据面板，展示数据源入口和抓包工作台入口。
4. 点击产出物面板，说明规则卡、核查结果和报告都可以作为产出物沉淀。
5. 打开产品经理 F 的手机聊天，发送问题，展示 `/api/chat/constrained` 基于办公室后端状态返回受控回答。
6. 明确当前边界：办公室 UI 已接入后端，但抓包工作台仍为浏览器端解析，RAG 文档尚未做服务端向量库持久化。

### 2.4 成功信号

- 观众能理解 A-F 角色和后端阶段的关系。
- 观众能理解办公室只是统一入口，财务和网络才是已稳定的规则控制样例。
- 不把抓包后端集中解析、RAG 向量库持久化、任意文件逐行解析讲成已完成能力。

## 3. 场景二：财务资料审阅

### 3.1 目标用户

- 财务审阅、内控、审计辅助场景的业务观众。
- 关注大模型是否会照抄错误数据的产品/技术观众。

### 3.2 输入资料

使用 W4 资产目录：

- 训练资料：`finance_v1` 合成财务训练集，完整训练集为 960 行。
- 待核查资料：`demo_artifacts/w4_demo_assets/finance/huaxin_audit_package.csv`。
- 真值表：`demo_artifacts/w4_demo_assets/finance/truth_table.json`。
- 推荐提问：`demo_artifacts/w4_demo_assets/finance/prompts.md`。

推荐报告问题：

```text
请基于华信咨询待审资料包，生成一份年度财务分析与审阅报告，并指出营业成本、资产负债配平、现金跨期、存货占比和应收增长是否存在异常。
```

### 3.3 业务流程

1. 用户查看训练资料预览。
2. 系统学习或加载财务规则。
3. 用户上传华信咨询待审资料包。
4. 系统运行规则核查，命中异常。
5. 用户输入报告问题。
6. 系统运行 A/B 双轨。
7. 用户对比 A 轨错误报告与 B 轨合规报告。

### 3.4 预期命中规则

| 规则 | 说明 | 演示讲法 |
|---|---|---|
| `R01` | 进销存勾稽 | 第 3 期营业成本写成 3,000，但应为 2,000 |
| `R02` | 资产负债配平 | 第 5 期资产总计比负债加权益多 500 |
| `R04` | 现金跨期滚动 | 第 1 期期末现金与第 2 期期初现金不一致 |
| `R06` | 行业画像 | 咨询公司期末存货占资产 35%，偏离行业常态 |
| `R07` | 比率背离 | 应收账款同比大幅增长而收入增长有限 |

### 3.5 A/B 对比重点

- A 轨风险：报告可能照抄错误营业成本 3,000，并基于错误数据继续分析。
- B 轨控制：规则先命中异常，Projector 修正硬勾稽错误，报告用槽位回填；营业成本应显示为 2,000。
- 讲述重点：不是让模型“更会写”，而是让模型不能随意使用未经规则确认的关键数值。

### 3.6 可展示产出

- 规则卡：解释 R01/R02/R04/R06/R07 的业务含义。
- 违规清单：每条违规对应行号、规则、实际值、期望值和中文说明。
- 双轨报告：A 轨错误值标红，B 轨展示修正后结论和干预日志。
- 下载报告：Markdown 报告用于交付留痕。

## 4. 场景三：网络 NetFlow 核查

### 4.1 目标用户

- 网络安全、流量审计、协议质量控制场景的技术观众。
- 关注大模型是否会生成违反协议/物理常识记录的观众。

### 4.2 输入资料

使用 W4 资产目录：

- 内置训练资料：`E:\yanchh\model_control\NetNomos\data\cidds_wk2_normal_10k.csv`。
- 归档规则库：`forge/rulesets/network_cidds/golden/rules.json`。
- 待核查资料：`demo_artifacts/w4_demo_assets/network/netflow_rule_anomaly_upload.csv`。
- B 轨兜底样本：`demo_artifacts/w4_demo_assets/network/network_b_track_reference_sample.json`。
- 推荐提问：`demo_artifacts/w4_demo_assets/network/prompts.md`。

推荐报告问题：

```text
请基于我上传的待核查 NetFlow 资料，生成或抽取 10 条 CIDDS 风格记录，并说明哪些记录违反 UDP Flags、Packets/Bytes 物理上下界或 DNS 端口身份规则；同时给出规则约束后的合规版本。
```

### 4.3 业务流程

1. 用户确认内置 CIDDS 训练资料。
2. 系统加载归档 NetNomos 自发现规则。
3. 用户上传待核查 NetFlow CSV。
4. 系统运行新资料核查。
5. 用户运行 A/B 双轨对比。
6. 系统展示 A 轨违规 NetFlow 与 B 轨 0 违规合规样本或约束生成结果。

### 4.4 预期规则

| 规则 | 说明 | 演示讲法 |
|---|---|---|
| 协议蕴含 | `Proto=UDP` 时不应携带 TCP Flags | 裸模型容易把协议字段混在一起 |
| 物理上界 | `Bytes <= 65535 * Packets` | 字节数不能超过包数带来的物理上限 |
| 物理下界 | `Bytes >= 42 * Packets` | 每个包至少有基础开销 |
| DNS 身份 | 端口 53/DNS 身份应一致 | 端口和服务标签不能互相矛盾 |

### 4.5 A/B 对比重点

- A 轨风险：生成 10 条 NetFlow 时可能出现 UDP 带 TCP Flags、Bytes 超上界、端口 53 非 DNS 身份等问题。
- B 轨控制：优先由 LeJIT/约束路径生成；若本机 bundle 不可用，回退到归档合规样本并保留干预说明。
- 讲述重点：规则控制不仅用于财务数值，也适用于网络协议和结构化记录生成。

## 5. 三场景串讲脚本

### 5.1 一分钟版本

```text
我们先用办公室 UI 展示一个多智能体协作流程：A 负责编排，B 接数据，C 学规则，D 验规则，E 出报告，F 做受控问答。然后进入财务和网络两个稳定 demo。财务场景证明模型不能照抄错误财务数字，网络场景证明模型不能生成违反协议和物理约束的 NetFlow。共同点是：规则可查看、违规可解释、B 轨输出可追溯。
```

### 5.2 五分钟版本

1. 办公室开场：说明角色和后端阶段映射。
2. 财务上传：展示华信咨询资料包和 `dataSourceId`。
3. 财务核查：展示 R01/R02/R04/R06/R07 命中。
4. 财务双轨：强调 A 轨照抄错误、B 轨修正和白名单终检。
5. 网络上传：展示 NetFlow 待核查资料。
6. 网络双轨：强调协议蕴含和物理上下界。
7. 收束：办公室已经接入同一套 SSE/job/report/chat 能力，形成统一产品体验。

## 6. 已知边界与讲述禁区

- 可以说明办公室 UI 已完成主集成：页面会触发 `office_demo` 后端 workflow、消费 SSE/job result，并调用受控聊天接口。
- 不要说当前可以解析任意上传 PDF/Word/PCAP 并逐行进入规则管线；W4 稳定演示仍使用场景管线和固定资产。
- 不要说网络 B 轨一定实时调用 LeJIT；应说明 LeJIT 不可用时使用归档合规样本保持演示稳定。
- 不要说受控聊天已经具备完整语义级合规推理；当前重点是数值白名单校验和降级可用。
- 不要在演示中依赖后端重启后的历史 job；当前 store 为内存实现。

## 7. 验收口径建议

| 验收项 | 可接受结果 |
|---|---|
| 办公室故事是否讲清 | A-F 角色与后端阶段关系清楚，且明确已接入能力和剩余边界 |
| 财务核查是否稳定 | 能看到华信资料包上传、规则命中、A/B 报告差异 |
| 网络核查是否稳定 | 能看到 NetFlow 上传、规则核查、A 轨违规/B 轨合规对比 |
| 接口口径是否准确 | 端点、入参、出参不与当前后端实现冲突 |
| 边界是否诚实 | 抓包后端解析、RAG 持久化、任意文件解析等未实现能力标为后续项 |
